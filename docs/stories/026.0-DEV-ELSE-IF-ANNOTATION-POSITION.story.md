# 026.0-DEV-ELSE-IF-ANNOTATION-POSITION: Support Prettier-Compatible Else-If Annotations

**GitHub Issue**: #4

## Release Goal

**Formatter Compatibility** - Ensure the plugin works seamlessly with popular code formatters like Prettier, allowing developers to maintain both code quality and traceability without conflicts.

## How This Story Contributes

This story resolves another Prettier compatibility issue where Prettier's automatic formatting conflicts with the `require-branch-annotation` rule's expectations for else-if statement annotations. When Prettier decides to wrap an else-if statement (typically based on line length), it moves annotations from before the `else` keyword to between the `else if` condition and the statement body. This creates the same chicken-and-egg problem as with catch clauses, forcing developers to choose between formatting and linting compliance.

By supporting both annotation positions (before else keyword OR between else-if and body), the plugin becomes formatter-aware while maintaining strict traceability requirements.

## User Story

**Format**: So that I can use Prettier formatting without breaking traceability validation, as a plugin developer, I want the `require-branch-annotation` rule to accept else-if annotations in either position (before the `else` keyword or between `else if` and the statement body).

**INVEST Criteria Compliance**:

- **Independent**: Can be developed independently - only affects else-if annotation detection logic
- **Negotiable**: Implementation approach (fallback detection vs configuration option) can be refined during development

- **Estimable**: Clear scope - modify annotation detection for else-if nodes, add tests
- **Small**: Localized change to annotation gathering logic, completable in one iteration

## Implementation Notes (Optional)

**Technical Approach**:

Modify `gatherBranchCommentText` in `src/utils/branch-annotation-helpers.ts` to add special handling for else-if statements:

1. **Current behavior** (for all branch types including IfStatement):
   - Gets comments before the node using `sourceCode.getCommentsBefore(node)`
2. **New fallback for else-if** (when no before-comments found or no annotations in before-comments):
   - If node is an IfStatement that is part of an else-if chain (parent.alternate === node)
   - AND no annotations found before the node
   - Get comments between the `else if (condition)` and the statement body
   - Extract text from those comments
   - Apply same annotation regex tests (`/@story\b/`, `/@req\b/`)

3. **Auto-fix adjustment**:
   - For else-if statements, detect if Prettier would wrap the statement
   - Insert annotations in position that Prettier will preserve
   - Calculate proper indentation based on context

**Prettier Behavior Analysis**:

- Prettier wraps else-if statements when line length exceeds configured width
- When wrapped, Prettier places comments between condition and body
- Single-line else-if statements keep annotations before else keyword
- This behavior is consistent across Prettier versions

**Testing Strategy**:

- Test annotations before else keyword (existing behavior)
- Test annotations between else-if condition and body (new behavior)
- Test Prettier-formatted code with wrapped else-if statements
- Test single-line else-if statements (no wrapping)
- Test missing annotations trigger errors in both positions
- Test auto-fix produces Prettier-compatible output
- Test nested if/else-if chains
- Test edge cases: multiple else-if in chain, else without if, etc.

**Edge Cases**:

- Single-line else-if (no wrapping needed)
- Multi-line else-if (Prettier wraps)
- Chained else-if statements (multiple in sequence)
- else-if with block statements vs single statements
- Nested if/else-if structures
- Multiple annotations in different positions

**Real-World Test Case** (from dry-aged-deps):

```javascript
// Single-line else-if statements with @supports annotations
let suggestion;
// @supports prompts/014.0-DEV-INVALID-OPTION-ERROR.md REQ-DID-YOU-MEAN
if (arg === "--json") suggestion = "--format=json";
// @supports prompts/014.0-DEV-INVALID-OPTION-ERROR.md REQ-DID-YOU-MEAN
else if (arg.startsWith("--format")) suggestion = "--format";
```

This pattern should be properly detected and validated without requiring braces or BlockStatement.
