# 010.4-DEV-UNIFIED-FUNCTION-RULE-AND-ALIASES: Unified Rule, Aliases, and @supports-First Model

## Release Goal

_Core Validation: Provide a single canonical function-level rule with backward-compatible aliases and an @supports-first annotation model_

This story formalizes the unified function-level rule `traceability/require-traceability`, its legacy aliases (`require-story-annotation` and `require-req-annotation`), and the `@supports`-first annotation model from a feature perspective. It ensures that users, documentation, and implementation all align on a single canonical rule while preserving backward compatibility for existing configurations.

## How This Story Contributes

This story strengthens the "Configure and Adopt" journey phase by:

- Giving users a clear recommendation for which rule key to use for function-level traceability.
- Ensuring legacy rule names continue to work without diverging behavior.
- Clarifying how `@supports` relates to older `@story` / `@req` annotations.

It builds on the core function-annotation story (003.0) and multi-story support (010.2, 010.3), tying together implementation, configuration, and user guidance.

## User Story

**Format**: So that I can configure function-level traceability checks without confusion, as a Developer or Team Lead, I want a single canonical rule and clear guidance on how legacy rule keys and @supports annotations behave.

**INVEST Criteria Compliance**:

- **Independent**: Builds on existing function-annotation rules and @supports implementation but focuses on configuration, wiring, and guidance.
- **Negotiable**: Details of presets and alias behavior can be tuned during implementation.
- **Valuable**: Reduces confusion for new and existing users configuring the plugin.
- **Estimable**: Scope is clear  unify rule wiring, document behavior, and align presets.
- **Small**: Can be completed within a single iteration/sprint.
- **Testable**: Behavior can be verified via rule tests and integration tests that exercise all rule keys.

## Requirements and Acceptance Criteria

- **REQ-ANNOTATION-REQUIRED** (extends 003.0): `require-traceability` is the canonical function-level rule, and legacy keys are aliases of the same engine
  - [x] **Canonical Rule**: `traceability/require-traceability` is defined as the canonical function-level rule in code and documentation.
  - [x] **Legacy Aliases**: `traceability/require-story-annotation` and `traceability/require-req-annotation` are implemented as backward-compatible aliases that share the same underlying engine as the canonical rule.

- **REQ-UNIFIED-ALIAS-ENGINE**: Alias wiring reuses the canonical implementation and keeps metadata accurate
  - [x] **Alias Metadata**: Alias rule metadata (`meta.docs`, `meta.messages`, `meta.schema`, `meta.deprecated`, `meta.replacedBy`) is merged so that legacy docs and options remain accurate while behavior is unified.
  - [x] **Implementation Source of Truth**: Listener behavior is sourced from `src/rules/require-traceability.ts`.

- **REQ-SUPPORTS-FIRST-MODEL** (extends 010.2, 010.3): The unified rule and its aliases accept `@supports` alongside legacy `@story` / `@req`
  - [x] **@supports Acceptance**: The unified rule and its aliases accept `@supports` annotations as satisfying story and requirement presence checks alongside legacy `@story` / `@req` where applicable.

- **REQ-PRESETS-CANONICAL-RULE**: Presets and guidance point to the canonical rule key
  - [x] **Presets**: `traceability.configs.recommended` and `traceability.configs.strict` enable `traceability/require-traceability` and treat the legacy keys as compatibility shims (enabled only to keep older configs working as documented).

- **REQ-MIGRATION-RULE-NAMING** (extends 010.3): Migration rule canonical naming and deprecated alias are supported
  - [x] **Migration Rule Alias**: `traceability/prefer-supports-annotation` is documented and wired as the canonical migration rule, with `traceability/prefer-implements-annotation` retained as a deprecated alias.

- **REQ-DOCS-CONSISTENCY**: Documentation consistently describes canonical rule, aliases, and @supports preference
  - [x] **Documentation Alignment**: README, API Reference, and Traceability Overview clearly describe:
    - `require-traceability` as the canonical rule.
    - Legacy keys as aliases sharing the same engine.
    - `@supports` as the preferred annotation form for new and multi-story code.

- **REQ-INTEGRATION-TESTS**: Integration tests validate consistent behavior across canonical rule and aliases
  - [x] **Integration Tests**: Integration tests (e.g., via ESLint CLI or RuleTester) verify that enabling each of the three function-level keys produces consistent behavior on representative fixtures, including @supports and @story/@req combinations.
