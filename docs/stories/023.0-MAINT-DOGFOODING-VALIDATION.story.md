# 023.0-MAINT-DOGFOODING-VALIDATION: Enable Plugin Self-Validation with Traceability Rules

**Story Type**: Internal Developer Experience (Plugin Developer - NOT end-user facing)  
**Story Map**: #file:plugin-developer-story.map.md (Release 0.5: Quality Foundation)  
**Commit Convention**: Use `chore:` or `refactor:` tags, NOT `feat:` - this is an internal quality improvement

## Release Goal

**Development Quality & Credibility** - Ensure the plugin demonstrates best practices by validating its own codebase with the same traceability rules it provides to users, establishing trust through dogfooding.

## How This Story Contributes

This story addresses a critical gap in the project's quality assurance: the plugin provides comprehensive traceability validation features but doesn't enforce them on its own codebase. By enabling self-validation, we:

1. **Catch annotation errors early** - Automated validation of 1,737+ existing annotations prevents defects
2. **Demonstrate credibility** - Shows users that we trust our own tools enough to use them
3. **Improve developer experience** - Reduces manual review burden and catches issues in CI/CD pipeline
4. **Enable incremental improvement** - Provides visibility into annotation quality through automated reporting

This directly supports the plugin's mission of enforcing traceability while maintaining code quality standards.

## User Story

**Format**: So that I can trust the plugin validates annotations correctly and catch annotation errors early in development, as a plugin developer (maintainer/contributor), I want the plugin to enforce its own traceability rules on its codebase using the recommended preset.

**INVEST Criteria Compliance**:

- **Independent**: Can be developed without blocking other features (uses existing plugin and preset infrastructure)
- **Negotiable**: Implementation details flexible (could use recommended or strict preset, could configure individual rules)
- **Valuable**: Delivers clear value through automated validation and credibility demonstration
- **Estimable**: Scope is well-defined - enable preset, suppress violations, fix incrementally
- **Small**: Core enablement can be completed in one iteration (fixing all violations is separate work)
- **Testable**: Success verified through lint runs showing traceability rules active and dogfooding validation test passing

## Implementation Notes

### Configuration Approach

The recommended approach is to spread the `recommended` preset after plugin registration:

```javascript
module.exports = [
  js.configs.recommended,
  // ... existing config objects ...
  {
    files: ["**/*.ts", "**/*.tsx"],
    plugins: {
      ...(plugin.rules ? { traceability: plugin } : {}),
    },
    rules: {
      // ... existing rules ...
    },
  },
  // Add the traceability preset at the end
  ...(plugin.configs?.recommended || []),
  // ... test file overrides and ignores ...
];
```

### Incremental Fix Process

1. Enable preset and commit configuration change
2. Run lint to identify all violations
3. Add eslint-disable suppressions to all violating files
4. Commit suppressions (allows CI to pass)
5. For each file:
   - Remove suppression
   - Fix violations
   - Verify lint passes
   - Commit fix
6. Track progress with suppression report

### Testing Strategy

The dogfooding validation test should:
- Verify `eslint.config.js` contains the preset spreading
- Lint a known source file and verify traceability rules are active
- Use ESLint's `calculateConfigForFile` to confirm rules are enabled

### Performance Considerations

- Enabling traceability rules may increase lint time slightly
- Build step required before linting adds to workflow time
- Consider caching built plugin in CI to minimize overhead

### Risk Mitigation

- **Risk**: Enabling rules breaks CI immediately with 1,737+ annotations to validate
  - **Mitigation**: Use suppression strategy to defer fixes while enabling validation
- **Risk**: Suppressions might never get removed
  - **Mitigation**: Track suppressions and add to project health metrics
- **Risk**: Conditional plugin loading might fail in some environments
  - **Mitigation**: Test in both development and CI environments

## Story Rationale

Dogfooding (using our own product) is a critical practice for establishing credibility and ensuring quality. The current gap where the plugin doesn't validate its own annotations:

1. **Undermines trust** - Users may question why we don't use our own features
2. **Misses errors** - 1,737+ annotations could contain errors we'd never detect
3. **Creates technical debt** - Without automated validation, annotation quality degrades over time
4. **Reduces confidence** - Developers can't rely on automated checks during code review

Enabling self-validation demonstrates that we trust our own tools and provides the same quality benefits to our codebase that we promise to users.
