# 020.0-DEV-TEST-ANNOTATION-VALIDATION: Validate Test File Traceability Annotations

## Release Goal

**Test Traceability** - Extend traceability validation to test files, ensuring tests are properly linked to requirements through annotations and naming conventions.

This story enforces the test annotation conventions already in use across the project, ensuring test files maintain proper `@supports` annotations and that test structure (describe blocks and test names) includes traceability information for visibility in test output.

## How This Story Contributes

While the core plugin validates production code annotations, test files have unique traceability needs. Tests serve as executable requirements validation, so maintaining clear links between tests and requirements is essential. This story extends the "Validate Annotations" journey phase to test files, ensuring the conventions that make test output traceable are enforced consistently.

By validating test annotations, this story ensures that:

- Test reports clearly show which requirements are being tested
- QA engineers can trace test coverage back to requirements
- Developers maintain traceability discipline in test code
- Test files serve as reliable documentation of requirement implementation

## User Story

**Format**: So that test output clearly shows which requirements are being tested and I can ensure complete test coverage of requirements, as a QA Engineer, I want the ESLint plugin to validate that test files have proper `@supports` annotations and include requirement references in describe blocks and test names.

## Requirements and Acceptance Criteria

- **REQ-TEST-FILE-SUPPORTS**: Validate test files have `@supports` annotations listing tested requirements
	- [ ] **File-Level Annotations**: Validates test files have `@supports` annotations at file level

- **REQ-TEST-DESCRIBE-STORY**: Validate `describe()` blocks include story reference in their description string
	- [ ] **Describe Block Story References**: Validates `describe()` blocks include story reference (e.g., "Story 009.0-DEV-...")

- **REQ-TEST-IT-REQ-PREFIX**: Validate `it()` test names start with `[REQ-XXX]` format
	- [ ] **Test Name Requirement Prefixes**: Validates `it()` test names start with `[REQ-XXX]` requirement ID

- **REQ-TEST-SUPPORTS-VALID**: Validate `@supports` annotations reference existing story files and requirements
	- [ ] **Integration**: Works with existing plugin infrastructure and configuration
	- [ ] **Error Messages**: Provides clear, actionable error messages for violations

- **REQ-TEST-PATTERN-DETECT**: Detect test files vs production code files for selective validation
	- [ ] **Quality Standards**: Rules follow ESLint best practices and perform efficiently

- **REQ-TEST-FRAMEWORK-COMPAT**: Support multiple test frameworks (Jest, Mocha, etc.)
	- [ ] **Framework Support**: Works with Jest, Mocha, and other common test frameworks

- **REQ-TEST-NESTED-DESCRIBE**: Handle nested `describe()` blocks appropriately (only top-level or all levels)
	- [ ] **Nested Describe Support**: Nested `describe()` blocks are handled according to documented rules

- **REQ-TEST-ERROR-CONTEXT**: Provide helpful context in error messages (which requirement is missing, etc.)
	- [ ] **Error Messages**: Provides clear, actionable error messages for violations

- **REQ-TEST-FUNCTION-ANNOTATIONS**: Function-level annotation rules from story 003 apply to helper functions and utilities within test files
	- [ ] **Consistency**: Test helper functions remain subject to function-level rules, while test framework callbacks derive traceability from file-level `@supports` and naming conventions

- **REQ-DOCUMENTATION**: Rule behavior and configuration options are documented
	- [ ] **Documentation**: Rule behavior and configuration options are documented

## Implementation Notes

**Test File Detection**:

- Match files in `tests/`, `test/`, `__tests__/` directories
- Match files with `.test.ts`, `.test.js`, `.spec.ts`, `.spec.js` extensions
- Configurable patterns for custom project structures

**Validation Approach**:

- Create new ESLint rule `require-test-traceability`
- Parse JSDoc comments to find `@supports` annotations
- Traverse AST to find `describe()` and `it()` CallExpressions
- Validate describe block descriptions contain story patterns (e.g., "Story XXX.X-")
- Validate test names start with `[REQ-XXX]` pattern

**Test Framework Compatibility**:

- Detect `describe`, `it`, `test`, `context` function calls
- Handle framework-specific variations (Jest's `describe.each`, etc.)
- Support both `it()` and `test()` for test definitions

**Error Message Examples**:

- "Test file must have @supports annotation listing tested requirements"
- "describe() block should reference story (e.g., 'Story 009.0-DEV-...')"
- "Test name should start with requirement ID (e.g., '[REQ-MAINT-DETECT] ...')"

**Configuration Options**:

- `testFilePatterns`: Custom patterns for identifying test files
- `requireDescribeStory`: Whether story reference in describe is required (default: true)
- `requireTestReqPrefix`: Whether [REQ-XXX] prefix is required (default: true)
- `describePattern`: Custom pattern for story reference in describe blocks
