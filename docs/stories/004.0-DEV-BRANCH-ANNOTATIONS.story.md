# 004.0-DEV-BRANCH-ANNOTATIONS: Code Branch Annotation Validation

## Release Goal

_Core Validation: Provide essential ESLint rules that enforce @story and @req annotations on functions and code branches_

This story implements ESLint rules that validate significant code branches (if/else blocks, try/catch blocks, switch cases, loops) have proper traceability annotations. It extends traceability enforcement beyond functions to ensure complex logic paths can be traced back to their requirements.

## How This Story Contributes

This story completes the core annotation enforcement by ensuring not just functions, but also significant logical branches within functions are traceable. It enables comprehensive requirement validation by ensuring that every code path can be traced to its originating story and requirement, supporting the system prompt's emphasis on branch-level traceability.

## User Story

**Format**: So that I can trace complex logic and conditional code paths back to requirements, as a Developer, I want an ESLint rule that validates significant code branches have @story and @req annotations in comments.

**INVEST Criteria Compliance**:

- **Independent**: Can be developed after function annotations (depends on 001.0, 002.0, 003.0 patterns)
- **Negotiable**: Branch significance criteria and annotation requirements can be refined
- **Valuable**: Delivers comprehensive traceability coverage beyond function-level
- **Estimable**: Scope is clear - ESLint rule for branch annotation validation
- **Small**: Can be completed within a single iteration/sprint
- **Testable**: Rule can be tested with various code branch patterns using RuleTester

## Requirements and Acceptance Criteria

- **REQ-BRANCH-DETECTION**: Detect significant code branches (if/else, try/catch, switch, loops)
  - [x] **Core Functionality**: ESLint rule detects significant code branches missing @story or @req annotations

- **REQ-COMMENT-ASSOCIATION**: Associate inline comments with their corresponding code branches
  - [x] **Integration**: Rule works with complex nested code structures and various programming patterns

- **REQ-ANNOTATION-PARSING**: Parse @story and @req annotations from branch comments
  - [x] **Quality Standards**: Rule follows ESLint development best practices and performance guidelines

- **REQ-SUPPORTS-ALTERNATIVE**: Accept @supports <story-file> <REQ-ID> as an alternative to separate @story and @req annotations
  - [x] **Alternative Format Support**: Rule accepts @supports <story-file> <REQ-ID> as a valid alternative to separate @story and @req annotations

- **REQ-SIGNIFICANCE-CRITERIA**: Define criteria for which branches require annotations
  - [x] **User Experience**: Clear error messages indicate which branch needs annotation and why

- **REQ-NESTED-HANDLING**: Handle nested branches and complex control flow structures
  - [x] **Error Handling**: Gracefully handles edge cases like nested branches and complex conditionals

- **REQ-CONFIGURABLE-SCOPE**: Allow configuration of which branch types require annotations
  - [x] **Documentation**: Rule documentation with examples of annotated branches and configuration

- **REQ-PERFORMANCE-OPTIMIZATION**: Efficient processing of large files with many branches
  - [x] **Performance**: Efficient processing of large files with many branches

- **REQ-SWITCH-CASE-ANNOTATION**: Each individual case block in switch statements requires annotation
  - [x] **Switch Statement Handling**: Individual case blocks require annotations, default case must be annotated, only last case before code block needs annotation for fall-through patterns

- **REQ-SWITCH-DEFAULT-REQUIRED**: Default case in switch statements must have annotation
  - [x] **Default Case Required**: Default case in switch statements must have annotation

- **REQ-SWITCH-FALLTHROUGH**: For fall-through cases, only the last case before code block needs annotation
  - [x] **Fall-through Handling**: For fall-through cases, only the last case before code block needs annotation

- **REQ-LOOP-ANNOTATION**: All loop types (for/while/do-while/for-in/for-of) require annotations
  - [x] **Loop Annotation Flexibility**: All loops (for/while/do-while/for-in/for-of) require annotations, allowed on either loop body or loop statement

- **REQ-LOOP-PLACEMENT-FLEXIBLE**: Loop annotations accepted on either loop body or loop statement
  - [x] **Flexible Placement**: Loop annotations accepted on either loop body or loop statement

- **REQ-TERNARY-EXCLUDED**: Ternary operators (? :) never require annotations
  - [x] **Ternary Operator Exclusion**: Ternary operators never require annotations (not considered significant branching)

- **REQ-ARROW-FUNCTION-BRANCH-INCLUDED**: Branches (if/else, loops, try/catch, etc.) inside arrow functions require annotations even when the arrow function itself is anonymous and excluded from function-level annotations
  - [x] **Arrow Function Branch Inclusion**: Branches inside arrow functions require annotations even when the arrow function itself is anonymous

- **REQ-ASYNC-CATCH-INCLUDED**: Catch blocks in async/await contexts require annotations like regular catch blocks
  - [x] **Async Error Handling**: Catch blocks in async/await contexts require annotations like regular catch blocks

- **REQ-LOGICAL-OPERATOR-EXCLUDED**: Short-circuit operators (&&/||) and optional chaining (?.) never require annotations
  - [x] **Logical Operator Exclusion**: Short-circuit evaluation (&&/||) and optional chaining (?.) never require annotations

- **REQ-NESTED-FUNCTION-INHERITANCE**: Anonymous nested/inner functions (e.g., callbacks, IIFEs) inherit parent function's annotation; named nested functions require their own explicit annotations
  - [x] **Nested Function Inheritance**: Anonymous nested/inner functions inherit parent function's annotation; named nested functions require their own annotations

## Implementation Notes (Optional)

Additional context for developers:

**Development Resources**:

- See [Custom ESLint Rules Development Guide](../custom-rules-development-guide.md) for comprehensive patterns
- Review [Working with the AST](../custom-rules-development-guide.md#working-with-the-ast) for control flow node visitors
- See [Accessing Source Code](../custom-rules-development-guide.md#accessing-source-code) for comment association

**Implementation Details**:

- Leverage patterns established in 003.0-DEV-FUNCTION-ANNOTATIONS for consistency
- Use AST visitor pattern to identify significant control flow nodes (IfStatement, TryStatement, ForStatement, etc.)
- Consider branch complexity/significance thresholds (configurable)
- Handle inline comments vs. block comments for branch annotations
- Support various comment styles (// and /\* \*/) for branch annotations using `sourceCode.getCommentsBefore()`
- Implement smart detection of "significant" vs. trivial branches
- Consider performance impact on large files with many conditional statements
- Provide clear guidance on where to place branch annotations (before branch, inline, etc.)

**Branch-Specific Rules** (REQ-SWITCH-CASE-ANNOTATION, REQ-SWITCH-DEFAULT-REQUIRED, REQ-SWITCH-FALLTHROUGH, REQ-LOOP-ANNOTATION, REQ-LOOP-PLACEMENT-FLEXIBLE):

- Switch statements: Each case block requires annotation, default case must be annotated, fall-through cases only need annotation on last case before code
- Loops: All for/while/do-while/for-in/for-of require annotations, placement flexible (loop body or loop statement)
- Ternary operators: Never require annotations (REQ-TERNARY-EXCLUDED)
- Arrow function branches: Branches inside any arrow function require annotations (REQ-ARROW-FUNCTION-BRANCH-INCLUDED)
- Async error handling: Catch blocks in async/await require annotations like regular catch blocks (REQ-ASYNC-CATCH-INCLUDED)
- Logical operators: Short-circuit (&&/||) and optional chaining (?.) never require annotations (REQ-LOGICAL-OPERATOR-EXCLUDED)
- Nested functions: Anonymous nested functions inherit parent's annotation; named nested functions require their own annotations (REQ-NESTED-FUNCTION-INHERITANCE)

Example annotation patterns:

```javascript
// @story docs/stories/001.0-DEV-EXAMPLE.story.md
// @req REQ-ERROR-HANDLING
if (error) {
  // error handling logic
}

try {
  // @story docs/stories/001.0-DEV-EXAMPLE.story.md
  // @req REQ-API-CALL
  await apiCall();
} catch (error) {
  // @story docs/stories/001.0-DEV-EXAMPLE.story.md
  // @req REQ-ERROR-RECOVERY
  handleError(error);
}

// Using @supports format (alternative to @story + @req)
// @supports docs/stories/014.0-DEV-INVALID-OPTION-ERROR.story.md REQ-DID-YOU-MEAN
if (arg === "--json") suggestion = "--json";
// @supports docs/stories/014.0-DEV-INVALID-OPTION-ERROR.story.md REQ-DID-YOU-MEAN
else if (arg.startsWith("--format")) suggestion = "--format";

// Switch statement example (REQ-SWITCH-CASE-ANNOTATION, REQ-SWITCH-DEFAULT-REQUIRED)
// @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-SWITCH-CASE-ANNOTATION
switch (action) {
  // @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-ACTION-CREATE
  case "create":
    createItem();
    break;
  // @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-ACTION-DELETE
  case "delete":
    deleteItem();
    break;
  // @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-ACTION-DEFAULT
  default:
    handleUnknown();
}

// Fall-through example (REQ-SWITCH-FALLTHROUGH)
// @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-SWITCH-FALLTHROUGH
switch (status) {
  case "pending":
  case "processing":
  // @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-STATUS-IN-PROGRESS
  case "validating":
    handleInProgress();
    break;
}

// Loop example (REQ-LOOP-ANNOTATION, REQ-LOOP-PLACEMENT-FLEXIBLE)
// @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-LOOP-PROCESS-ITEMS
for (const item of items) {
  processItem(item);
}

// Nested function inheritance (REQ-NESTED-FUNCTION-INHERITANCE)
// @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-OUTER-FUNCTION
function outer() {
  // Inner function inherits REQ-OUTER-FUNCTION
  function inner() {
    if (condition) {
      // This branch also inherits REQ-OUTER-FUNCTION
    }
  }

  // Explicit override
  // @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-DIFFERENT-REQUIREMENT
  function specialized() {
    // This uses REQ-DIFFERENT-REQUIREMENT instead
  }
}

// Examples of excluded constructs (never need annotations)
// Ternary operator (REQ-TERNARY-EXCLUDED) - no annotation needed
const value = condition ? "yes" : "no";

// Anonymous arrow function (REQ-ARROW-FUNCTION-EXCLUDED) - no function annotation needed
array.map(() => doSomething());

// Test framework callbacks (REQ-ARROW-FUNCTION-EXCLUDED) - no function annotation needed (default)
describe("Feature", () => {
  it("should work", () => {
    // test code
  });
});

// Named arrow function (REQ-ARROW-FUNCTION-EXCLUDED) - DOES need function annotation
// @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-NAMED-ARROW
const handler = () => doSomething();

// Arrow function with branches (REQ-ARROW-FUNCTION-BRANCH-INCLUDED) - branches need annotations
const processor = () => {
  // @supports docs/stories/004.0-DEV-BRANCH-ANNOTATIONS.story.md REQ-BRANCH-IN-ARROW
  if (condition) {
    process();
  }
};

// Logical operators (REQ-LOGICAL-OPERATOR-EXCLUDED) - no annotation needed
const result = (isReady && execute()) || fallback();
user?.profile?.settings?.theme;
```

## Configuration (REQ-CONFIGURABLE-SCOPE)

This ESLint rule can be configured to enforce annotations only on specific branch types. For example, to enforce only on `IfStatement` and `ForStatement`:

```js
// .eslintrc.js
module.exports = {
  rules: {
    // @req REQ-CONFIGURABLE-SCOPE
    "traceability/require-branch-annotation": [
      "error",
      { branchTypes: ["IfStatement", "ForStatement"] },
    ],
  },
};
```

```js
// .eslintrc.js
module.exports = {
  rules: {
    // @req REQ-CONFIGURABLE-SCOPE
    "traceability/require-branch-annotation": [
      "error",
      { branchTypes: ["IfStatement"] },
    ],
  },
};
```

Invalid Configuration Behavior:

- If an unsupported or misspelled branch type is provided in `branchTypes`, the rule reports a configuration error during ESLint initialization with a message like:  
  `traceability/require-branch-annotation: Invalid branch type "InvalidType" in configuration. Supported branch types are: IfStatement, SwitchStatement, ForStatement, WhileStatement, DoWhileStatement, TryStatement, ForInStatement, ForOfStatement.`
