# 003.0-DEV-FUNCTION-ANNOTATIONS: Function Annotation Validation

## Release Goal

_Core Validation: Provide essential ESLint rules that enforce @story and @req annotations on functions and code branches_

This story implements the core ESLint rules that validate functions have proper @story and @req annotations. It provides the fundamental traceability enforcement that ensures all functions can be traced back to their originating requirements and stories.

## How This Story Contributes

This story delivers the primary value proposition of the plugin by implementing the core validation rules for function annotations. It enables the "Write Code" journey phase by ensuring developers receive immediate feedback when they create functions without proper traceability annotations, establishing the foundation for bidirectional traceability.

## User Story

**Format**: So that I can ensure all functions in my codebase are traceable to requirements, as a Developer, I want ESLint rules that validate functions have @story and @req annotations in their JSDoc comments.

**INVEST Criteria Compliance**:

- **Independent**: Can be developed after plugin foundation and configuration (depends on 001.0, 002.0)
- **Negotiable**: Rule strictness and annotation format can be refined during implementation
- **Valuable**: Delivers core traceability enforcement for functions
- **Estimable**: Scope is clear - coordinated ESLint rules with defined behavior
- **Small**: Can be completed within a single iteration/sprint
- **Testable**: Rules can be thoroughly tested with ESLint's RuleTester

## Requirements and Acceptance Criteria

- **REQ-FUNCTION-DETECTION**: Detect the following function-like constructs for annotation validation, shared by both rules: `FunctionDeclaration`, `FunctionExpression`, `MethodDefinition` (including class constructors and lifecycle methods), `TSDeclareFunction`, `TSMethodSignature`. Anonymous arrow functions (e.g., callbacks like `array.map(() => {})`) are excluded by default from traceability requirements. Named arrow functions (e.g., `const handler = () => {}`) require annotations like other function declarations
  - [x] **Core Functionality**: ESLint rule `require-traceability` is implemented and exported in the plugin, enforcing @story and @req annotations (or @supports) on functions, with `require-story-annotation` and `require-req-annotation` exported as backward-compatible aliases

- **REQ-JSDOC-PARSING**: Parse JSDoc comments to extract @story and @req annotations, using a common parsing strategy for both rules
  - [x] **Quality Standards**: Rules follow ESLint rule development best practices

- **REQ-ANNOTATION-REQ-DETECTION**: Implement and test advanced detection heuristics in the req-annotation utilities so that @req (or equivalent @supports) markers are discovered even when not present in the immediate JSDoc block. This includes `linesBeforeHasReq` to scan preceding source lines for @req markers in comments, `parentChainHasReq` to traverse parent AST nodes (and their leading comments) when direct JSDoc parsing does not find a req, and `hasReqAnnotation` orchestration logic that first checks direct JSDoc/@supports annotations then falls back to these heuristics. These heuristics MUST be covered by dedicated unit tests to guard against regressions
  - [x] **Integration**: Rules work with TypeScript, JavaScript, and mixed codebases

- **REQ-ANNOTATION-REQUIRED**: The `require-traceability` unified rule requires traceability annotations (@story + @req, or @supports) on all in-scope functions, with `require-story-annotation` and `require-req-annotation` maintained as backward-compatible aliases. The unified rule ensures functions carry proper traceability annotations
  - [x] **User Experience**: Clear, actionable error messages guide developers to fix issues

- **REQ-CONFIGURABLE-SCOPE**: The `require-traceability` rule (and its aliases) supports configurable scope semantics including which function kinds require annotations (e.g., exported only vs. all detected kinds) and optional constraints based on configuration (e.g., complexity threshold if applicable)
  - [x] **Error Handling**: Gracefully handles malformed JSDoc comments and edge cases

- **REQ-EXPORT-PRIORITY**: The `require-traceability` rule (and its aliases) supports an `exportPriority`/equivalent option so that exported functions are prioritized for enforcement over internal ones
  - [x] **Documentation**: Rule documentation with examples and configuration options

- **REQ-ERROR-LOCATION**: The `require-traceability` rule (and its aliases) reports errors at the function name (or closest equivalent for anonymous constructs) for precise error location
  - [x] **Error Reporting**: Errors are reported at precise function name locations

- **REQ-TYPESCRIPT-SUPPORT**: Support TypeScript-specific function syntax and decorators, including `TSDeclareFunction` and `TSMethodSignature`, with consistent handling across the rule
  - [x] **TypeScript Compatibility**: TypeScript-specific syntax fully supported

- **REQ-TEST-CALLBACK-EXCLUSION**: Anonymous arrow functions passed as direct callbacks to known test framework functions are excluded from function-level annotation requirements by default, controlled by the `excludeTestCallbacks` option (default: `true`). Recognized test function identifiers (and their `.concurrent` variants where applicable) include: shared core (`it`, `test`, `describe`, `suite`), focused variants (`fit`, `ftest`, `fdescribe`, `fsuite`), skipped variants (`xit`, `xtest`, `xdescribe`, `xsuite`), and additional aliases and lifecycle hooks (`context`, `specify`, `before`, `after`, `beforeEach`, `afterEach`, `beforeAll`, `afterAll`). Vitest's `bench` is intentionally **not** excluded - callbacks passed to `bench(...)` behave like regular functions and must carry their own `@story`/`@supports` annotations (or satisfy nested-function inheritance rules) unless `excludeTestCallbacks` is disabled. Nested anonymous callbacks inside recognized test framework callbacks (for example, an inner anonymous arrow inside an `it(…)` callback) may inherit their parent function's annotation when they are effectively anonymous. Callbacks passed to custom wrapper helpers (for example, a local `withDescribe(…)` function that internally calls `describe(…)`) are **not** treated as recognized test callbacks and are subject to normal function-level annotation requirements unless they qualify for nested anonymous inheritance. The function-annotation helpers and `require-story-annotation` rule expose an `additionalTestHelperNames` option that accepts an array of helper names which should be treated as additional recognized test helpers when `excludeTestCallbacks` is true, participating in the same exclusion semantics as built-in test functions (except that `bench` callbacks are never excluded even if listed here)
  - [x] **Test Framework Callback Exclusion**: Implementation satisfies REQ-TEST-CALLBACK-EXCLUSION, excluding anonymous arrow callbacks passed directly to recognized test framework functions from function-level annotation requirements by default (configurable via `excludeTestCallbacks`, default: `true`) while **not** excluding Vitest `bench` callbacks; behavior is validated by helper-level and rule-level tests, including coverage for nested callbacks and local wrapper helpers (for example, callbacks passed to a `withDescribe` helper that internally calls `describe`)
  - [x] **Custom Test Helper Exclusion**: The function-annotation logic and ESLint rule expose a configuration option (`additionalTestHelperNames`) that allows projects to specify additional test helper function names which should be treated as excluded callbacks when `excludeTestCallbacks` is enabled (default: true). This behavior is validated by helper-level and rule-level tests, and bench callbacks remain always-enforced even if listed as additional helpers

**Implementation Details**:

- Use @typescript-eslint/utils for AST parsing to handle TypeScript syntax
- Leverage ESLint's JSDoc utilities for comment parsing via `sourceCode.getCommentsBefore()`
- Support function declarations and function expressions (excluding arrow functions), as well as `MethodDefinition`, `TSDeclareFunction`, and `TSMethodSignature`
- Consider performance impact of JSDoc parsing on large codebases
- Implement configurable options for function scope (exported only, all functions, complexity threshold)
- Handle edge cases: anonymous function expressions, IIFE, generator functions, async function declarations/expressions
- Arrow functions are explicitly excluded from traceability requirements by default
- Provide clear error messages that include function name and missing annotation type
- The `require-traceability` rule is the unified implementation, with `require-story-annotation` and `require-req-annotation` maintained as backward-compatible aliases that reference the same underlying rule logic; the current plugin exports follow this unified/alias model
