# 028.0-DEV-ANNOTATION-PLACEMENT-STANDARDIZATION: Standardize Annotation Placement Inside Block Braces

**GitHub Issue**: #7

## Release Goal

**Formatter Compatibility** - Ensure the plugin works seamlessly with popular code formatters like Prettier, allowing developers to maintain both code quality and traceability without conflicts.

This story contributes to the "Validate Annotations" phase of the developer journey by establishing a clear, unambiguous annotation placement standard that eliminates visual confusion and works seamlessly with code formatters. It supersedes the dual-position workarounds (025.0, 026.0) with a unified architectural approach, making traceability rules simpler to learn and more consistent to apply.

## How This Story Contributes

This story resolves a fundamental visual ambiguity issue in the current annotation placement rules. Currently, the plugin allows annotations in different positions relative to block braces, creating confusion about annotation scope:

- **Else blocks**: Annotations between `}` and `else {` are ambiguous - do they annotate the else branch, the first statement, or an inner block?
- **Catch blocks**: Must use inside-brace placement due to Prettier constraints (handled by 025.0)
- **Other blocks**: Typically use before-brace placement

This inconsistency makes the annotation rules harder to learn and creates visual ambiguity about what code is being annotated. By standardizing on "first-line-inside-brace" placement for ALL block types, the plugin achieves:

1. **Visual clarity**: Annotation scope is unambiguous - always starts at the brace
2. **Consistency**: Same rule applies to if/else/try/catch/switch/functions
3. **Formatter-friendly**: Prettier accepts this placement without modification
4. **Easy to teach**: Simple rule - "annotation is first line inside brace"

This story supersedes the dual-position workarounds in 025.0 and 026.0 with a unified architectural approach.

## Implementation Notes

**Architectural Decision**:

This story represents a fundamental shift from "before-brace" to "inside-brace" as the preferred annotation placement pattern. This change:

1. **Supersedes** the dual-position workarounds in 025.0 and 026.0
2. **Unifies** placement rules across all block types
3. **Simplifies** the mental model for developers
4. **Eliminates** visual ambiguity about annotation scope

**Migration Strategy**:

Implementation should be phased to maintain backward compatibility:

- Add configuration option with default to existing behavior
- Provide auto-fix migration capability
- Document benefits and migration path
- Eventually deprecate old approach after widespread adoption

**Testing Considerations**:

- Verify Prettier accepts inside-brace placement (confirmed in issue #7)
- Ensure backward compatibility with existing codebases
- Test all block types (if/else/try/catch/switch/function/loop)
- Validate auto-fix correctly handles indentation
