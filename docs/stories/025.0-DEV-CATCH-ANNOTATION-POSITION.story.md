# 025.0-DEV-CATCH-ANNOTATION-POSITION: Support Prettier-Compatible Catch Clause Annotations

**GitHub Issue**: #4

## Release Goal

**Release 0.6: Formatter Compatibility** - Ensure the plugin works seamlessly with popular code formatters like Prettier, allowing developers to maintain both code quality and traceability without conflicts.

## How This Story Contributes

This story resolves a critical usability issue where Prettier's automatic formatting conflicts with the `require-branch-annotation` rule's expectations for catch clause annotations. Currently, the rule requires annotations to be placed before the `catch` keyword, but Prettier consistently moves these comments inside the catch block body. This creates a chicken-and-egg problem where formatting breaks linting, forcing developers to choose between:

1. Disabling Prettier for affected files
2. Keeping `eslint-disable` suppressions (defeating traceability)
3. Manually fighting formatter on every commit

By supporting both annotation positions (before catch keyword OR as first comments inside catch block), the plugin becomes formatter-aware while maintaining strict traceability requirements.

## User Story

**Format**: So that I can use Prettier formatting without breaking traceability validation, as a plugin developer, I want the `require-branch-annotation` rule to accept catch clause annotations in either position (before the `catch` keyword or as the first comments inside the catch block).

**INVEST Criteria Compliance**:

- **Independent**: Can be developed independently - only affects CatchClause annotation detection logic
- **Negotiable**: Implementation approach (fallback detection vs configuration option) can be refined during development
- **Valuable**: Eliminates formatter conflicts and removes need for suppressions in catch blocks
- **Estimable**: Clear scope - modify annotation detection for CatchClause nodes, add tests
- **Small**: Localized change to annotation gathering logic, completable in one iteration
- **Testable**: Clear acceptance criteria with specific before/after formatting scenarios

## Acceptance Criteria

- [ ] **Before-Catch Position**: Annotations placed immediately before the `catch` keyword are detected and validated (existing behavior preserved)
- [ ] **Inside-Catch Position**: Annotations placed as the first comments inside the catch block body are detected and validated (new fallback behavior)
- [ ] **Prettier Compatibility**: Code formatted by Prettier with default settings passes validation without requiring manual intervention
- [ ] **Position Priority**: When annotations exist in both positions, the before-catch position takes precedence (prevents duplicate reporting)
- [ ] **Auto-Fix Compatibility**: Auto-fix inserts annotations in a position that Prettier will preserve (inside catch block preferred for Prettier users)
- [ ] **No Regression**: All existing catch clause tests continue to pass, annotations in other branch types (if/switch/try/etc.) remain unaffected
- [ ] **Documentation**: Rule documentation explains both valid annotation positions and Prettier compatibility

## Requirements (Current Implementation or To Be Implemented)

- **REQ-DUAL-POSITION-DETECTION**: Check for annotations before catch keyword AND inside catch block body
- **REQ-FALLBACK-LOGIC**: If annotations not found before catch, check first comments inside catch block
- **REQ-POSITION-PRIORITY**: Prefer before-catch annotations when present in both positions to avoid duplicate errors
- **REQ-PRETTIER-AUTOFIX**: Auto-fix should insert annotations inside catch block to survive Prettier formatting
- **IMPL-BRANCH-ANNOTATION-INFO**: Existing `getBranchAnnotationInfo` function in `src/utils/branch-annotation-helpers.ts` currently checks comments before node
- **IMPL-GATHER-COMMENT-TEXT**: Existing `gatherBranchCommentText` function collects comments but only from before the node
- **IMPL-CATCHCLAUSE-HANDLER**: CatchClause is already in `DEFAULT_BRANCH_TYPES` array and handled by the rule

## Implementation Notes (Optional)

**Technical Approach**:

Modify `gatherBranchCommentText` in `src/utils/branch-annotation-helpers.ts` to add special handling for `CatchClause` nodes:

1. **Current behavior** (for all branch types including CatchClause):
   - Gets comments before the node using `sourceCode.getCommentsBefore(node)`
2. **New fallback for CatchClause** (when no before-comments found or no annotations in before-comments):
   - If `node.type === 'CatchClause'` AND no annotations found before
   - Get first comment tokens inside `node.body`
   - Check if first statements in body are comments
   - Extract text from those comments
   - Apply same annotation regex tests (`/@story\b/`, `/@req\b/`)

3. **Auto-fix adjustment**:
   - For CatchClause nodes, insert annotations as first lines inside the catch block body
   - Calculate proper indentation based on catch block's first statement
   - Format: `${catchBodyIndent}// @story <story-file>.story.md\n`

**Testing Strategy**:

- Test annotations before catch keyword (existing behavior)
- Test annotations inside catch block (new behavior)
- Test Prettier-formatted code with annotations inside catch block
- Test missing annotations trigger errors in both positions
- Test auto-fix produces Prettier-compatible output
- Test that try block annotations remain unaffected
- Test edge cases: empty catch blocks, catch with parameter, nested try/catch

**Edge Cases**:

- Empty catch blocks (`catch { }`)
- Catch with parameter (`catch (error) { }`)
- Catch blocks with only non-annotation comments
- Nested try/catch structures
- Multiple annotations in different positions

**Prettier Behavior Documentation**:

- Prettier version tested: v3.4.2
- Default configuration: 120 char width, single quotes, 2-space indent
- Prettier consistently moves before-catch comments to first line inside catch block
- This behavior is stable across Prettier versions
