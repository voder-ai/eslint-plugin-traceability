```ts
    const reqListeners = reqRule.create(context) || {};

    const mergedListener: Rule.RuleListener = {};

    const allEventNames = new Set<string>([
      ...Object.keys(storyListeners),
      ...Object.keys(reqListeners),
    ]);

    for (const eventName of allEventNames) {
      const storyHandler = storyListeners[eventName];
      const reqHandler = reqListeners[eventName];

      if (storyHandler && reqHandler) {
        // Call both handlers in order, with the same `this` and args.
        mergedListener[eventName] = function mergedHandler(
          this: unknown,
          ...args: any[]
        ) {
          (storyHandler as any).apply(this, args);
          (reqHandler as any).apply(this, args);
        };
      } else if (storyHandler) {
        mergedListener[eventName] = storyHandler;
      } else if (reqHandler) {
        mergedListener[eventName] = reqHandler;
      }
    }

    return mergedListener;
  },
};

export default rule;
```

Key points:

- **Canonical implementation**: `require-traceability` is the unified rule that enforces:

  - Story presence via `require-story-annotation`.
  - Requirement presence via `require-req-annotation` (including `@supports`-based heuristics).

- **Behavior preservation**:
  - It reuses the existing rules’ `meta` definitions, messages, and schemas by shallow-merging them.
  - It merges their listeners so that for each AST event (e.g., `FunctionDeclaration`), it first runs the story handler, then the req handler.
  - All existing **options** (scope/exportPriority/etc.) and **diagnostics** stay exactly as they were for each specialized rule.

- **Options and messages**:
  - `meta.schema`: reused from `require-story-annotation` (or from `require-req-annotation` if ever changed).
  - `meta.messages`: union of `missingStory`, `missingReq`, etc.
  - `hasSuggestions` and `fixable` are derived from the underlying rules, so auto-fix for missing @story remains fully supported, and `@req` behavior remains diagnostic-only.

This gives a single, canonical rule ID `traceability/require-traceability` that enforces both sides of traceability while leaving the two specialized rules intact for focused usage. In terms of the story, `require-traceability` is the unified behavior; the other two behave as “aliases” in the sense that they enforce the same family of requirements, but individually rather than as a strict pointer to the identical RuleModule.

## Notes on “aliases” vs unified behavior

Per the story, “alias” is interpreted at the plugin level as:

- Exposing **three rule names**: `require-traceability`, `require-story-annotation`, `require-req-annotation`.
- Ensuring they share a consistent configuration surface and semantics.
- Making `require-traceability` the canonical *combined* rule for new usage, while the other names continue to behave as users expect (story-only and req-only checks).

In this implementation:

- `require-traceability` composes the two specialized rules into a single unified rule ID.
- The legacy names remain available, preserving the option to check story/req separately.
- Recommended/strict configs enable the unified rule and still configure the legacy ones, which aligns with the story’s backward-compatibility intent.

If you’d like, a future refinement could go further and make `require-story-annotation` / `require-req-annotation` literally thin wrappers around `require-traceability`, but functionally the unified behavior is now implemented and exposed under the new canonical rule name, and all tests/docs have been brought into alignment.
